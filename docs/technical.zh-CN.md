# 技术原理与逆向经验

**简体中文** | [English](technical.md)

本文说明最小修改方案及相关逆向依据。实机结果和资料来源见[实测记录与来源](evidence.zh-CN.md)。

## 暖启动镜像与菜单构建

Sony 在 60 MiB 的 `nflasha5` 分区保存 Warm Boot Image。本机 2.02 的补丁跳表与 Backup 值都正确时，暖恢复仍沿用旧的 TypeRK 四项 Page1，频带节点 `0x285` 未创建；取电池约 30 秒也未保证重新构建。备份并用 Sony 原厂工具使 WBI 入口失效后，下次启动没有暖恢复标志，全局和屏幕当前 Page1 均为 TypeNB 五项，`0x285` 已启用。机主确认原生菜单及 5 GHz 功能。安全验收见[暖镜像恢复流程](wbi.zh-CN.md)。这是 2.02 实机结果，2.03 尚未完成同等条件的重新验收。

## 原生菜单：TypeNB

静态比较发现，第一代 A7C 的 Wi-Fi 页面选择 **TypeNB**，其中包含“频带”；ZV-E10 选择的 **TypeRK** 则不包含。将 `CautionConfig.so` 文件偏移 `0xD778E4` 的 `20` 改为 `1B`，就是切换原生页面选择，不需要移植 A7C 代码或另写菜单。

第二层开关是 Backup 属性 `0x01071C54`。分析的 28 份 ZV-E10 原厂模板均为 `00`，26 份 A7C 模板中有 24 份为 `01`，AF1 除外。在实测 ZV-E10 上，TypeNB 配合属性 `01` 即可显示并使用 Sony 原生 2.4/5 GHz 页面。保留正确的原生频带对象映射，不采用早期把菜单行改指向其他类型对象的实验方案。

频带菜单用于直连，不是连接路由器时强制 5 GHz 的总开关。Sony 的 [A7C 说明](https://helpguide.sony.net/ilc/2020/v1/en/contents/TP1000156044.html)列出了原生直连功能的适用范围。路由器连接另由当前配置、可用网络及驱动规则决定。

## Backup 数据库与 B/C 启动路径

Sony 的 BK4 配置数据库按属性 ID 保存值。本文的 **B/C 是研究简称**，取自 `0x00A5000B`、`0x00A5000C` 的末位，并非声称 Sony 正式采用该命名。它们为不同网络路径选择 1–26 号 NVRAM 文件。B 用于正常相机热点 GO，C 用于普通访问点连接 STA；不是分别控制 2.4 和 5 GHz。

代码中，网络服务按工作模式将选择信息传给 `libWlanResource`；其 `get_bcmdhd_insmod_args` 路径拼接 `bcm4339_*_%02d.txt` 编号文件名，用于驱动初始化。三组原厂目录包含不同射频校准组合，应保留，不混用校准数据，也不整份替换为 A7C 的 NVRAM。

已有操作使用以下服务接口：

```python
original = bytes(camera.readBackup(property_id))
camera.writeBackup(property_id, value)
camera.saveBackup(property_id >> 16)
assert bytes(camera.readBackup(property_id)) == value
```

通过 Sony 属性接口调用保存机制，不直接十六进制编辑两份 BK4 文件。先保存本机每个属性的准确原值及完整私密数据库快照。正常使用也会改变数据库其他字段；最终核查发现多项非 Wi-Fi 属性变化，没有将它们重置。

中国大陆 `B=2/C=22` 分别选择 **XR/76**、**XR/143**。ZV-E10 2.02 的活动热点和路由器连接实际读到了这两个修订，功能测试成功。原 `09/09` 选择 XR/83，在已有基线中只提供 2.4 GHz。见[地区表](regions.zh-CN.md)。

## 硬件及原厂文件对照

公开监管清单分别记录了 [ZV-E10 的 Type1DR 模块（IFT）](https://www.ift.org.mx/node/19562)及 [A7C 的 Type1DR 模块（NTC 清单，印刷第 187 页）](https://region7.ntc.gov.ph/wp-content/uploads/2024/01/RCE_08312021.pdf)。固件材料和 ZV-E10 运行驱动对应 Broadcom BCM4339。该证据支持共享模块系列和芯片平台，不能单凭它证明所有地区主板、天线或认证相同。

A7C 与 ZV-E10 2.03 的正常 `bcm4339.bin`、`bcmdhd.ko`、supplicant 及已检查网络配置文件逐字节相同。78 份编号 NVRAM 中，相同编号的 XR/regrev 一致；文本存在 `ed_thresh5g=-80/-90` 差异，但未证明它是解锁开关或发射功率限额。已验证最小方案不需要替换无线固件或 NVRAM。

Sony [官方规格](https://helpguide.sony.net/ilc/2020/v1/en/contents/TP1000156734.html)区分 A7C 不同地区的单频、双频产品。模块名称或模板标签不能替代修改后 ZV-E10 的无线型号核准。

## 按 inode 提取文件及核对版本

文件在分区内不一定连续存储。应按 **inode**（记录文件实际数据块位置的文件系统元数据）读取，并按具体文件系统处理间接块或 extent，或使用正确的 ext 文件系统读取器。从猜测的首块开始连续切片可能夹入其他块，得到看似合理但内容错误的 ELF 文件。提取后核对长度、ELF 加载段及整文件哈希，并与独立导出的副本比较。

区分离线 eMMC 分析使用的 ext4 式 inode 提取，与相机实测 `/usr` 的挂载信息：**`/dev/nflasha15` 上的 ext2**。补丁位置是逻辑文件偏移，不是物理分区偏移。历史分区候选曾通过 inode 数据块映射目标字节；普通 USB 安装不需要这条路线。

## CLM 研究及未解决问题

CLM 是 Broadcom 编译后的无线监管数据。分析固件中有 26 条 XR 修订记录，与编号 NVRAM 对应。CLM 文件头位于 `0x79058`，虚拟地址为 `0x1F9058`，API `9.10.139`、编译器 `1.26.11`。该镜像的虚拟地址减 `0x180000` 可换算为文件偏移。已解析文件头、表结构和顶层信道范围。

完整的 **XR 修订 → locale → 允许信道、功率及 DFS** 链尚未可靠解码。locale 是监管数据中按频段等组织规则的结构。不能把顶层 5 GHz 范围直接分配给每个 XR：原厂 ZV-E10 的 XR/83 运行时没有 5 GHz 条目，正是反例。[OpenWrt bcmclm 源码](https://lxr.openwrt.org/source/firmware-utils/src/bcmclm.c)仅作为格式参考，不是完整 Sony 地区解码器；本仓库未复制其代码。

后续中国大陆实机测试已证实 XR/76 和 XR/143 的功能，覆盖了旧记录中的“中国配置未测试”状态，但尚未解决发射功率、DFS/TPC、室内限制及当地型号核准。XR 是内部两字符代码，不能按 ISO 国家码翻译。也未证实跨国使用时相机会自动切换配置。

## 已放弃或不再需要的方案

- 临时 US/0 NVRAM 替换曾开启 5 GHz，但改变了信道集合，最终中国大陆方案不需要。最终核查已恢复原厂 NVRAM 并删除 US 运行副本。
- `viewUnified2` 虚表槽、许可和行工厂补丁属于探索，其中部分没有可见菜单效果，单槽 ELF 候选未部署。它们均不属于最终最小方案，也不能复用旧会话的运行地址。
- 修改 supplicant、P2P 配置、完整 BCM4339 固件或驱动，对已验证最小方案均不必要；这不等于证明所有可能补丁都完全无效。
- **整文件 `cp`** 曾报空间不足，将库截短为 11,173,888 字节。运行进程仍映射旧的已删除 inode，当时还能运行不能证明下次能启动。继续 USB 实验前，已通过硬件 fastboot 从机主备份恢复受损分区。
- 相机 BusyBox `dd` 没有可用的 `conv=notrunc`，seek 写入会截断文件，禁止用于此补丁。

## 持久 USB-C 单字节写入

完整原厂库恢复后，实测 ARM Linux 程序以 `O_RDWR` 打开已有固定路径，**不带 `O_CREAT` 或 `O_TRUNC`**；定位目标偏移，核对 `20`，写入 `1B`，调用 `fsync` 后再读回。退出码 10–16 分别表示打开、定位、读取、原值比较、写入、同步和验证错误。程序自身不计算整文件哈希，因此主机在前后核对。Wi-Fi 专用操作负责文件校验，会话生命周期交给 toolkit；属性快照、写入和保存只在 toolkit 实现一份，调用已有 PMCA-RE 方法。

实际目标库保留 inode 和完整长度，导出后与原厂仅有目标一字节不同；拔 USB、取电池冷启动后仍保留，原生菜单正常。fastboot 用于恢复此前失败实验，**普通 USB-C 单字节安装不需要 fastboot**。
